# PRD-评审建议：探针（Probe）V1.0

> 对 \`PRD.md\` 的工程与产品评审。分四类：**致命（不改会毁掉产品承诺）** / **必须补规格（不补无法开工）** / **架构减负** / **路线图重排**。
> 每条都给了可直接落进 PRD 的改法。

---

## 一、致命：置信度算法衡量的是“大家说法一致”，不是“这是真的”

PRD 2.2 把 **NAS（Network Agenda Setting，网络议程设置）** 用作属性一致性的算法载体。问题是：

- NAS 是传播学里研究“媒体议程网络如何影响公众认知网络”的理论，**它本身不是事实验证方法**。
- “多信源对同一事件核心属性（时间、人物、地点）的收敛度”——收敛度高只说明**信源之间抄得一样**。
- 十家媒体转载同一篇通稿时，收敛度是满分。此时置信度最高，而事实可能完全没被独立验证过。这就是**假共识（false consensus）**。

而“高置信度、不编造事实”是这个产品的第一卖点、也是与 Perplexity 拉开差距的唯一理由。用一个在数学上会奖励“抄得一致”的指标来给产品背书，方向就反了。

**改法**：置信度拆成三个可独立计算的分量，权重写死并公开：

| 分量 | 含义 | 计算方式 | 权重 |
|---|---|---|---|
| **独立性 I** | 有多少个**互不隶属**的信源 | 域名 → 媒体集团/稿源 owner 归并；\`I = 1 - exp(-n_owners / 3)\` | 0.35 |
| **一手性 P** | 是一手发布还是转载 | canonical URL、最早发布时间、标题相似度（>0.9 判转载） | 0.40 |
| **一致性 C** | 去重后各独立源在（实体, 数值, 时间）上是否吻合 | 仅作辅助，且**必须先完成去重** | 0.25 |

**并且加三条硬规则**（这是“不编造”得到工程化的地方）：

1. 每个数字必须能点回原文片段；抽不出原文的数字**不显示**，不填 0。
2. 数据缺失时显示“数据缺失”，不是 0，也不是“暂无数据”（后者会被读成“确实没有”）。
3. 置信度徽章必须可展开，列出具体信源清单 + 各自原文摘录 + 独立性判定依据。**不可展开的徽章等于装饰**。

## 二、致命：热度公式量纲不成立

\`热度分 = Magnitude + Deviance × 时间衰减因子\`

- Magnitude 是“绝对注意力增量”（无上界，可能 10 万），Deviance 是“背离基线的程度”（通常是比值或 z-score，量级 0～3）。**两者相加在数值上没有意义**，谁大谁说话。
- 衰减因子只乘在 Deviance 上，等于说量级不衰减。那么一个三天前爆过 100 万篇的话题会永久霸榜，而今天刚起来的 5 万篇永远进不了 Top N。榜单会死。

**改法**（可直接抄）：

\`\`\`
Mag  = log1p(articles_24h)                          # 压缩量纲
Dev  = (articles_24h - median_30d) / (MAD_30d + ε)  # 稳健 z-score，抗离群
raw  = 0.6 * pct90(Mag) + 0.4 * pct90(Dev)          # 两项各自 90 天分位归一，同量纲后再加权
score = raw * exp(-age_hours / τ)，  τ = 36h         # 衰减乘整体，不乘单项
\`\`\`

状态标签的阈值必须写进 PRD（否则 Phase 3 无法验收）：

| 标签 | 判据 |
|---|---|
| 爆发期 | \`r7 = 近 7 日均值 / 前 30 日均值\` > 2，且绝对值进 90 天 Top 5% |
| 长尾期 | 曾进过爆发期，当前 \`r7\` ∈ [1.0, 2.0] 且已持续 ≥ 5 天 |
| 争议态 | 见下条（需要 sentiment，不能只靠热度） |

## 三、致命：“争议态”的情感判断没有任何来源定义

PRD 说“展示正负面新闻数量对比图，不写分析只展示数据”。但**正负面的判定本身就是模型判断，也是一个幻觉源**。不说清楚用谁的情感分，这块就是产品里唯一一处“自己编数据却叫数据”的地方。

**改法**：明确写下数据来源与口径。

- 首选 **GDELT GKG 的 \`tone\` 原生字段**（免费、可复现、不是我们算的），直接按正/负/中性三档展示。
- 若自建分类器，必须写：模型名、语种覆盖、抽样人工校验准确率、以及**在 UI 上标注“情感为模型判定，非事实”**。
- 争议态的判据应该是“独立信源在价值判断上分裂”，不是“情感分数方差大”。最小可行版：\`负向信源数 / 总信源数\` ∈ [0.3, 0.7] 且独立源数 ≥ 5。

## 四、致命：让 LLM 直接吐 ECharts option，是幻觉放大器 + 性能瓶颈

PRD 2.4 与 4 的 Coder Agent 让模型输出完整 ECharts JSON 配置。两个问题：

1. **成本**：一个复合面板的 option 动辄几千 token，多图并发生成会显著吃延迟和费用，而 PRD 没写任何 token/费用上限。
2. **幻觉的真实形态不止“解析失败”**。更糟的是**语法合法但语义错**：绝对值当比率、时间轴倒序、饼图各项加总 ≠ 100、把两个不同量纲的指标放同一坐标轴。PRD 3 的容错只覆盖了 \`JSON.parse\` 失败这一种，覆盖不到上述任何一种。

**改法**：模型输出**受限图表 DSL**，前端编译器把 DSL 编译成 ECharts option。

\`\`\`ts
// 模型只能产出这个形状（zod schema 强校验，白名单枚举）
type ModuleSpec = {
  id: string;
  kind: "bar" | "line" | "pie" | "treemap" | "map" | "table" | "kpi";
  title: string;
  dataset: string;              // 只能引用 Analyzer 已产出的具名数据集
  encode: { x?: string; y?: string; series?: string; value?: string };
  note?: string;
};
\`\`\`

好处：幻觉的爆炸半径从“渲染出一张语法合法的错图”压缩到“选错图型或选错字段”，后者可以被规则拦截（如 pie 必须 value ≥ 0 且只允许一个 series）。token 降一个数量级，小模型就能跑。

## 五、必须补规格：流式协议没有定义，前端写不出来

“前端图表卡片长出来一块渲染一块”是产品体验的核心，但 PRD 没给传输契约。**必须是单一 SSE 连接上的多路事件**，不是多个 fetch（多个 fetch 无法保证顺序、无法与文本流对齐）。

建议直接写进 PRD 作为附录：

\`\`\`
event: text.delta    data: {"delta":"..."}
event: module.plan   data: {"id":"m1","kind":"line","title":"90天讨论度","w":6,"h":8}
event: module.ready  data: {"id":"m1","spec":{...},"data":{...},"sources":[...]}
event: module.error  data: {"id":"m1","reason":"schema_invalid","fallback":"table"}
event: done          data: {"confidence":0.72,"independent_sources":6}
\`\`\`

两条配套规则：

- \`module.plan\` 先落**骨架卡**（固定 id + 预估网格尺寸），\`module.ready\` 只替换内容。否则流式追加卡片会让 \`react-grid-layout\` 反复重排，用户正在拖的布局会跳。
- 流式生成期间禁用拖拽，\`done\` 之后解锁。

## 六、必须补规格：结构化抽取这一步完全缺席，而它才是 MVP 最大的工程风险

Phase 1 写的是“接入单一搜索 API（Tavily）+ 文本流式 + 一张折线图”。但 Tavily 返回的是**网页摘要文本**，不是结构化数据。从“摘要文本”到“折线图的数据点”中间那一步——**结构化抽取**——是整条链路里最贵、最不可靠的一环，PRD 一个字没提。

**改法**：Phase 1 明确写死抽取策略与降级路径。

1. 抽取 = 一次 \`generateObject\`（JSON mode）+ zod 校验，temperature 0，不重试超过 1 次。
2. 校验失败 → 降级为“原文卡片列表 + 摘要”，**不留空白面板**。
3. 每张卡片底部固定挂 \`N sources\` + 展开看原文。这既是卖点，也是抽取失败时用户的自然出口。

顺便：`Tavily` 的 rate limit 与多源并发失败策略 PRD 全篇没写（GDELT DOC API 实测 1 req/5s，超了直接 429）。需要一条：`任一源失败 → 面板照常出，缺失模块标记“该源不可用”，不阻塞整体`。

## 七、架构减负：删掉 LangChain.js

PRD 4 写的是“Vercel AI SDK（处理流式）+ LangChain.js”。这两套抽象在 App Router 里混用，典型后果是**编排状态在 LangChain 里、流式输出在 AI SDK 里，两边不同步**，调试成本远超收益。

四个 Agent 本质上就是一条显式异步流水线 + 一个状态机，不需要框架：

\`\`\`ts
// 一条 pipeline，每步是纯函数，输入输出都用 zod 定义
route(query)                                        // → Intent
  → retrieve(intent)                                // → RawSource[]（并发 + 单源超时）
  → analyze(raw)                                    // → { datasets, confidence, sources }
  → compose(datasets)                               // → ModuleSpec[]
\`\`\`

保留 Vercel AI SDK 做 \`streamText\` / \`streamObject\` / tool calling 就够了。**LangChain.js 从架构里删掉。**

## 八、路线图重排：热点榜不该等到 Phase 3

现在的顺序是 Phase 1 搜索闭环 → Phase 2 多源与拖拽 → Phase 3 热度算法。

问题：**搜索型产品的回访理由几乎全靠“有个地方能看到今天在发生什么”**。热度榜是唯一不依赖用户 query 的入口（也是拉新入口）。放到第 6 个月，前五个月产品没有任何打开理由。

**改法**：把“热点榜 v0”提到 Phase 2——只做静态 Top N + 无状态标签（甚至只按文章量排序），不接完整公式。完整公式与状态机留在 Phase 3。同时 Phase 3 的 Neo4j 建议先不做：**pgvector 已经在栈里，实体关系图先用邻接表 + 2 跳查询就能出树状图**，多一个 Neo4j 是多一套运维。

## 九、缺失的非功能需求（PRD 需要补一节）

| 类别 | 必须写清楚的东西 |
|---|---|
| **成本** | 单次搜索的 LLM 调用次数上限、token 预算上限、每日调用总预算。当前架构（4 Agent + 每图生成）不设上限会失控 |
| **缓存** | 同一 query 的面板缓存 TTL（建议 6h）；命中缓存直接回放，不打 API |
| **限流** | 单用户 QPS、Tavily/GDELT 的配额与降速策略 |
| **可观测性** | 每个 Agent 步骤的耗时 / token / 失败率 / 降级次数。**没有这个指标，Phase 2 调优全靠猜** |
| **数据合规** | 抓取的新闻正文是否落库？落库的版权边界？只存 metadata + 摘要 + 原文链接是最稳的 |
| **空态** | 冷门词无数据时的面板长什么样（可行性分析已指出这是真实风险） |

---

## 十、验收标准（当前 PRD 缺一条能判定“高置信度”成立的标准）

建议直接写进 PRD：

1. 面板上任意一个数字，点击 2 次内必须能看到原始出处（URL + 原文片段）。
2. 抽不出原文的数字，出现率为 0。
3. 置信度徽章可展开，且信源清单与实际展示的数字一一对应。
4. 单一数据源失败时，面板仍能渲染出 ≥ 1 个模块，且明确标注缺失。

这四条能让“不编造事实”从口号变成可测的东西。

---

## 一句话结论

**PRD 的产品判断是对的（Generative UI + 克制分析 + 面向极客），但把最有差异化的两个承诺——“高置信度”和“热度状态”——都留在了伪代码级。** 建议先按本文第一、二、四条改这三个算法定义，再按第五、六条补两个协议，然后开工 Phase 1。
