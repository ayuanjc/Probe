# 探针（Probe）可行性分析 + 开源选型

> 结论先说：**可行，且不需要从零造轮子。** 数据层有免费金矿（GDELT + Wikipedia + RSS），展示层全是成熟库；真正的工作量在"中文全网采集"和"查询时序/预聚合"，不在可视化。

## 一、四个功能模块的技术判定

| 你的设想 | 可行性 | 落地方式 | 主要风险 |
|---|---|---|---|
| 搜索任意词 → 生成数据面板 | 高 | 关键词→多源并行检索→归一化→聚合指标→前端渲染 | 冷门词无数据；需要兜底"空态面板" |
| 全球新闻网数据 + 历史讨论度 | 高 | GDELT 15 分钟增量（全球多语言）+ Wikipedia pageviews + Reddit/HN | 历史回溯存储量；中文全网要自采 |
| 柱状图 / 树状图 / 全球地图 | 很高 | ECharts（bar/treemap/tree/sunburst）+ deck.gl / globe.gl | 无 |
| 捕捉热点词 + 热度/状态 | 高 | GDELT GKG themes + 增长率 → 状态机（爆发/升温/平稳/回落） | 热点"状态"必须自己定义阈值，数据源不给现成标签 |
| 模块化 / 用户自定义界面 | 高 | react-grid-layout（或 gridstack.js）+ 布局 JSON 存后端 | 布局 schema 版本兼容 |

## 二、数据源实测（本机已跑通）

已实际请求验证，不是纸面推测：

- **GDELT DOC 2.0 API** — `https://api.gdeltproject.org/api/v2/doc/doc?query=...&mode=artlist&format=json` → **HTTP 200，无需 key**，返回 title / url / domain / language / seendate。限制：**1 请求 / 5 秒**，超了直接 429（我实测撞到了）。
- **GDELT v2 15 分钟增量** — `https://data.gdeltproject.org/gdeltv2/lastupdate.txt` → 返回当前批次（实测 `20261023003000`）的 `.export.CSV.zip`（事件，含 ActionGeo 经纬度）、`.mentions.CSV.zip`、`.gkg.csv.zip`（主题/实体/语调）。**这是全球地图 + 历史讨论度的主数据源，免费、无 key、15 分钟更新。**
- **Wikipedia pageviews** — `https://wikimedia.org/api/rest_v1/metrics/pageviews/per-article/en.wikipedia/all-access/user/ChatGPT/monthly/2025010100/2026090100` → **HTTP 200**，返回逐月浏览量序列（ChatGPT：2025-01 = 2,568,792 → 2025-02 = 2,601,557 …）。这是"历史讨论度"最干净的免费时序。
- **BBC World RSS** — HTTP 200，标准 RSS。RSS 批量订阅是最便宜的补充源。
- **HN Algolia API** — HTTP 200，可查任意词的帖子数/时间分布（技术圈热度的好指标）。
- **Reddit** — 直连被拒（需 OAuth / 合适 UA）；**微博热搜** — 直连 403（需 cookie）。→ 中文/社媒层必须走自建采集 + 代理池，这是成本项。

### 需要付费或绕过的源
- X/Twitter：API 已基本付费墙；替代用 GDELT 的 `domain=twitter` 覆盖或 Bluesky/Mastodon 公开流。
- Google Trends：无官方 API，**pytrends 可用但经常被限流**，只作参考不作主数据。
- 新闻 API（NewsAPI / newsdata.io）：免费额度 100 req/day 级别，只适合补充。
- 百度指数/微信指数：无公开 API，只能人工或第三方数据商。

## 四、推荐架构（单机可跑，不必上云）

```
采集  gdelt-fetch(15min cron) ─┐
      rss-ingest              ├─► 归一化(title,url,domain,lang,ts,geo,entities,themes,tone)
      hotlist(DailyHotApi)    │
      wiki-pageviews          ┘
                                   │
存储  ClickHouse（或 DuckDB+Parquet 起步）
      raw_articles / agg_topic_daily / topic_registry
                                   │
检索  FastAPI：/search?q= → 多源 → topic_id → 指标
      指标：文章数、独立域名数、情感均值、地域分布、7/30 日增长率、状态标签
                                   │
前端  React + ECharts + deck.gl + react-grid-layout
      布局 JSON 存后端 → 用户自定义面板
```

**"讨论度指数"怎么定义（关键，别含糊）**：
`score = 0.5·norm(GDELT 文章数) + 0.3·norm(Wikipedia 浏览量) + 0.2·norm(HN/Reddit 提及)`，各分项用 90 天分位数归一化。
**"状态"怎么判**：`r7 = 近 7 日均值 / 前 30 日均值` → r7>2 且绝对值进前 5% = 爆发；1.3<r7≤2 = 升温；0.8≤r7≤1.3 = 平稳；r7<0.8 = 回落。

## 五、分期落地（每期都有可验收产物）

**第 1 期（3–5 天）· 能看见东西**
GDELT DOC API + Wikipedia pageviews 两个源跑通；输入词 → 出 4 张图（文章量柱状图、域名分布 treemap、90 天讨论度折线、情感分布）。验收：随便输一个词能出面板。

**第 2 期（1 周）· 有历史、有地图**
接 GDELT 15 分钟增量入库（ClickHouse）+ 每日聚合表；deck.gl 全球地图（ActionGeo 经纬度打点）；回填近 90 天。验收：地图上点密度真实、时间轴可回放。

**第 3 期（1 周）· 热点与状态**
接 DailyHotApi 热榜 + GKG themes 提取 + 增长率状态机；热点榜页面。验收：热点词带"爆发/升温/平稳/回落"标签，且能点进详情面板。

**第 4 期（1 周）· 模块化定制**
react-grid-layout + 布局 JSON 持久化 + 组件注册表（每张卡片是一个受注册的 widget）。验收：拖拽保存后刷新仍在，可增删卡片。

## 六、成本与硬风险

- **存储**：GDELT 单批约 4.9 MB（gkg 4.77 + export 0.08 + mentions 0.09），96 批/天 ≈ **474 MB/天压缩、约 2.5 GB/天原始**；90 天原始约 220 GB，ClickHouse 压缩后约 30–60 GB。单机 4C8G + 200 GB 盘够跑。
- **硬风险 1：中文全网采集**。微博/抖音/小红书/公众号都有反爬，"稳定采集"是持续维护成本，不是一次性开发。建议：第一版只做 GDELT（它已含中文媒体）+ RSS + 热榜接口，别一上来死磕。
- **硬风险 2：冷门词的查询延迟**。任意词实时扫全量不现实 → 必须"入库 + 预聚合 + 按词建倒排/向量索引"，首查慢、二次查快。
- **硬风险 3：GDELT 的坑**。DOC API 有 1 req/5s 限制；GEO 2.0 端点我实测 404（已不可用），全球地图请**改用 export.CSV 的 ActionGeo 字段自己聚合**，别指望现成 geo 接口。
- **许可**：GDELT 要求署名；GPL-3.0 项目（TrendRadar / newsfeed）改完对外分发要开源。

## 七、一句话建议

**先做一个"单页原型"证明手感**：GDELT + Wikipedia 两个源 + ECharts 四张图，一天能出。手感对了再投第 2、3 期的工程量；上来就搭 Dagster+ClickHouse 的话，两周后你只有管道没有产品。
